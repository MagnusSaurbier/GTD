# GTD App — Architecture (as built)

`docs/REQUIREMENTS.md` says *what* the app does; `docs/STYLEGUIDE.md` says how it *looks, moves
and reads* (binding for all UI — §5); this file says *how it is built*. Requirement IDs
(N1, I4, P5 …) refer to REQUIREMENTS.md.

**The code is the source of truth for signatures.** This file describes shape, direction and the
rules that no single signature can show. Where it disagrees with the code, the code is right and
this file is a bug — fix it (`CLAUDE.md` → "Keeping this file current").

**Nothing here was written with an Apple SDK.** The whole app was written in a Linux container
with Swift but no Xcode, so every file behind `#if canImport(SwiftUI)` / `UserNotifications` /
`AppIntents`, and all of `App/`, was written blind. It builds and launches on fixtures (Xcode 27,
2026-09-19); `TEST-INSTRUCTIONS.md` is the first Mac session's script and log, and
`docs/TRACEABILITY.md` marks such code **done (blind)**.

## 1. Stack

- Swift 6, strict concurrency (`swift-tools-version: 6.2`, language mode 6 on every target),
  SwiftUI, Observation (`@Observable`). Minimum **iOS 26 / macOS 26** (STYLEGUIDE decision #4:
  Liquid Glass APIs, no availability checks, no fallbacks).
- One multiplatform app target (`GTD`) generated by **XcodeGen** from `project.yml`.
  `GTD.xcodeproj` is git-ignored — never edit a pbxproj, edit `project.yml` and regenerate.
- All code lives in one local Swift package, `Packages/GTDKit`, split into 18 small targets.
  The app target is a thin shell. Everything non-UI builds and tests with plain
  `swift build` / `swift test`, on Linux as well as macOS.
- Only third-party dependency: [Yams](https://github.com/jpsim/Yams), pinned `exact("6.2.2")`.
- No database. The vault's markdown files are the single source of truth; the app keeps an
  in-memory `VaultSnapshot` rebuilt from files.

`GTDFixtures` is a production dependency of every Feature target because their `#Preview`s use it.
`GTDServices → GTDAppCore` is allowed (`VaultBackend` conforms to `GTDBackend`); the forbidden
direction is **Feature → GTDVault/GTDServices**: features never touch the file system, they are
developed against `InMemoryBackend` + `GTDFixtures`. There are no cycles.

## 3. Vault layout

All paths are relative to the vault root the user picks (the folder containing `Actions/`).
Defaults live in `VaultLayout` and are overridable in `GTD/Config.md`.

| Path | Content |
| --- | --- |
| `Inbox/<yyyy-MM-dd HHmmss>[-n].md` | one capture per file (C3). Frontmatter: `created`, optional `reviewReason` |
| `Actions/<Title>.md` | one note per action (A1) |
| `Archive/YYYY/MM/` | done actions older than 30 days (A5) |
| `Projects/<Area>/<Area>.md` | area note, frontmatter `kind: area` |
| `Projects/[<Area>/]<Project>/<Project>.md` | project note, frontmatter `kind: project`, `status` |
| `Knowledge/**` | free folder tree (I4) |
| `GTD/Config.md` | synced settings in frontmatter (contexts, on-the-go set, cap, routine times) |
| `GTD/Routines/<Name>.md` | routine templates (R1) |
| `GTD/RoutineLog/<yyyy-MM-dd>--<deviceID>.md` | routine log, one file per day **per device** (R5, N3) |
| `GTD/Reviews/<yyyy>/KW <ww>.md` | weekly review notes (§10.4) |
| `GTD/Trash/` | trashed inbox items. The app never hard-deletes a vault file. |

Device-local state (bookmark, undo journal, resumable review wizard state, notification
bookkeeping, per-device settings) lives in Application Support, **not** in the vault.

### Note formats

Action (A1, schema in REQUIREMENTS §5):

```markdown
---
status: next
contexts: [mac]
timeEstimate: 30
project: "[[Projects/Applications/DAAD/DAAD]]"
created: 2026-09-18T21:04:11+02:00
---
# Why?
…
# What?
- [ ] …
```

Project note (P2): frontmatter `kind: project`, `status`; body sections `# Outcome`, `# Why?`,
`# Steps` (checkbox list; a promoted step becomes `- [ ] text → [[Action title]]`),
`# Log` (`- 2026-09-18 Did X`).

Routine template (R1): frontmatter `time: "07:00"`; body is a checkbox list, one top-level item
per step, nested items are sub-steps. Step id = slug of the step text. All steps are done/skip
only (R4).

Routine log: frontmatter `entries:` list of `{routine, step, result: done|skipped, at}`.

**Round-trip rule (N2):** the codec preserves unknown frontmatter keys, key order and unknown
body sections byte-for-byte. Empty means absent or empty — never a fake default
(`timeEstimate: 0` is forbidden, STYLEGUIDE §1 "no lying defaults").

## 4. Module contracts

One block per target: what it owns, where to start reading, and the invariants that hold it
together. Public signatures are **not** repeated here — read the source and the module's own
`README.md`, which are updated in the same commit as the code.

### GTDModel — the domain, and all GTD semantics

`Core/` (`NoteID`, `Day`, `DayTime`, `VaultLayout`), `Entities/` (`Action`, `Project`, `Area`,
`InboxItem`, `Routine`, `RoutineLogEntry`, `GTDConfig`, `WeeklyReview`, `VaultSnapshot`,
`NotePassthrough`), `Commands/` (`GTDCommand`, the drafts, `InboxDecision`, `GTDError`,
`AppPrompt`, `VaultFileOp`), `Reducer/` and `Rules/`.

- **Every mutation in the app is one `GTDCommand`**, and `Reducer.reduce(snapshot, command, env)`
  is the only place that interprets one. The cap, waiting validation, completion effects,
  promotion, demotion when a project leaves `active`, archive eligibility and every refusal live
  there — never in a view, a backend or a model object.
- `Rules` holds the derived queries (`nextList`, `onTheGoNextList`, `chaseItems`, `visibleActions`,
  `deferredList`, `waitingList`, `stalledProjects`, `projectRows`, `sidebarCounts`,
  `signals(for:today:)`, `archiveCandidates`, `timeline`, `suggestsProject`, `isUndoable` …).
  They are pure, total-ordered (no reliance on sort stability) and each names its requirement ID.
- `Signal`/`SignalKind`/`SignalStep`/`StalenessPolicy` are semantics, not styling: the thresholds
  of STYLEGUIDE §2.2 live here, and `DesignSystem` only renders them.
- `Day`/`DayTime` use integer civil-calendar arithmetic. Anywhere a `Day` meets a real `Date`,
  the query takes `calendar: Calendar = .current` and the reducer passes `env.calendar`, so no
  result depends on the machine's time zone.
- `GTDModel` never produces markdown.

**`extraOps` vs. the snapshot diff.** `Reduction.extraOps` covers file effects that are not
snapshot entities (knowledge notes, the weekly-review note, trash moves). The rule that keeps
them from fighting the diff: **a path named in `extraOps` is owned by `extraOps`** — the diff
emits nothing for it. So every command that makes a note leave its collection emits its own move
(inbox filing, archiving, renaming, converting an action into a project), and a removed entity
that no `extraOp` mentions means "move the file to `GTD/Trash/`".

### GTDMarkdown — the codec (N2)

Reading goes through Yams; **writing never re-serialises**. `decode` stashes the whole original
file in `NotePassthrough`; `encode` decodes that original again into a reference entity and
patches only the lines whose decoded value differs. Consequences: `encode(decode(text)) == text`
byte for byte, and changing one field changes exactly one line. Entities with an empty
passthrough render from `NoteTemplates` and are then patched the same way.

`NoteCodec` is the entry point (one `decode*`/`encode` pair per entity, `noteKind(text:)` for
dispatch, `unknownContexts(in:known:)`, `routineLogName`). The pieces it is built from —
`FrontmatterDocument`, `BodySections`, `CheckboxList`, `Wikilink`, `RawText`, `YAMLScalar` — are
public and separately tested. Everything that touches a timestamp takes `timeZone:
TimeZone = .current`.

**Any change here must keep `GTDMarkdownTests`' round-trip, fidelity, patch and fuzz suites
green.** They are the only thing standing between a bug and the user's notes.

### GTDVault — the only code that touches the file system

`VaultStore` (protocol) / `FileVaultStore` (actor) own scanning, watching and committing;
`VaultFileSystem` abstracts I/O (`CoordinatedFileSystem` on Apple platforms via
`NSFileCoordinator`, `PlainFileSystem` and `InMemoryFileSystem` for tests and Linux);
`VaultIndex` + `VaultClassifier` + `VaultNoteParser` turn a folder tree into a `VaultSnapshot`;
`VaultBookmark` persists the security-scoped bookmark; `InboxWriter` writes a capture **without
loading the vault** (C1); `Platform/` holds the Apple-only implementations and the portable
stand-in they fall back to off Apple platforms.

- `commit(ops)` applies ops in order and is **all-or-nothing**: on failure it rolls back what it
  applied and rethrows; a failing rollback is `VaultError.rollbackFailed(reason:rollbackReason:)`
  and means the vault is in a mixed state — show it to the user, never retry silently. The
  returned inverse ops come back **already in undo order**.
- A `.move` never overwrites (`VaultError.destinationExists`); `.delete` of a missing file is a
  no-op, `.move` of a missing source throws.
- **Nothing here can hard-delete**: `VaultFileSystem` has no delete member. Keep it that way.
- `activate()` creates `VaultLayout.requiredFolders`, scans once and starts watching.
- Decode failures never lose a note: they become `VaultIssue`s. Use `VaultNoteParser`, not
  `NoteCodec` directly.

### GTDServices — reducer to files, and undo

`VaultBackend` (actor, conforms to `GTDBackend`) = `Reducer.reduce` → diff old/new snapshot →
`NoteCodec.encode` the changed entities → `VaultStore.commit(ops + extraOps)` → push the inverse
onto `UndoJournal`. `Housekeeping` runs the daily `archiveCompleted`.

- **One command is one commit**, so a rename and the project steps linking to the renamed note
  cannot come apart.
- A note is written only when its encoding changed, so untouched files keep their mtime.
- Undo journal entries carry a content hash per file they would touch and are refused as
  `ServiceError.undoStale` when any of them changed since (N3). It keeps 20 entries and is
  persisted in Application Support.
- A successful command publishes the reduced snapshot immediately; the store's scanned snapshot
  replaces it when it arrives.
- Collisions in `Archive/` and `GTD/Trash/` get a free name (app-owned folders); anywhere else a
  taken destination is `GTDError.titleCollision`.

### GTDAppCore — what the UI sees

`GTDBackend` (the protocol every backend implements: `snapshots()`, `currentSnapshot()`,
`perform(_:)`, `undo()`, `undoLabel()`), `AppModel` (`@MainActor @Observable`, handed to views
through `@Environment(AppModel.self)`), `InMemoryBackend` (reducer only — previews and tests) and
`UndoLabel` (one label table, shared by both backends).

**Command order.** `AppModel` runs commands one at a time, in call order. `send(deriving:)` builds
its command only once it is that command's turn: a caller that derives a whole entity from
`snapshot` — the autosaving action editor — **must** use it, or it will put an in-flight command's
fields back. `send` throws `GTDError` for flows that handle the refusal themselves (the cap sheet,
the waiting sheet); `perform`/`report` route it to `lastError`, which the shell shows in one alert.
Nothing is swallowed with `try?`.

## 5. UI conventions

**`docs/STYLEGUIDE.md` is binding** for every view: tokens, components, states, gestures, keys,
motion, copy, icons, accessibility, and its §9 checklist (run it before reporting a UI change
done). Where a brief or a doc and the style guide disagree on look, interaction or wording, the
style guide wins; where they disagree on module structure, data or contracts, this file wins.

- Colours are **code-defined** (`DesignSystem/Tokens/Colors.swift`: system semantic colours plus
  `Color.dynamic(light:dark:)`), so nothing depends on an asset catalog resolving.
  `DesignSystem/Resources/Colors.xcassets` carries the same values for Xcode tooling and
  `App/Assets.xcassets` repeats the accent as `AccentColor`.
- Every UI target owns its own `Resources/Localizable.xcstrings` (`bundle: .module`, English as
  key and default), so no two targets share a catalog. Catalogs are compiled by Xcode's build
  system, not by `swift build`: no test may assert on a resolved colour or a catalog lookup, and
  the `xcodebuild` step of `scripts/check.sh` is what validates them.
- A suggestion (dashed chip) is UI state only. It never reaches a draft or a command until the
  user confirms it — the +7 d follow-up is *suggested*; `WaitingInfo` exists only on confirmation.
- Every screen and component state has `#Preview`s backed by `GTDFixtures.sampleSnapshot`.
- The platform split (N5) is decided in the app shell; features use `#if os(iOS)` / size classes
  only for input style (swipe vs keyboard). Mac is keyboard-complete (STYLEGUIDE §3.6, §4.5).

### Platform guards

`swift build` / `swift test` must pass on **Linux**, so:

- **Foundation-only targets** — `GTDModel`, `GTDMarkdown`, `GTDStats`, `GTDFixtures`,
  `GTDAppCore`, `GTDServices`, and the pure parts of `GTDVault`, `GTDNotifications` — contain
  **no** `import SwiftUI`/`UIKit`/`AppKit`/`UserNotifications`/`AppIntents` at all.
- **UI and platform-only code** lives in files wrapped **entirely** in `#if canImport(SwiftUI)`
  (or `canImport(UserNotifications)`, `canImport(AppIntents)`), first line to last. Never a guard
  around part of a file.
- **Every target keeps at least one Linux-compilable file** holding the logic worth testing —
  the models listed in §4, and in `DesignSystem` the tokens' numbers, `Symbols`, `Copy`/`DateText`,
  `ChipState`, `BadgeContent`, `SignalPresentation`, `HeatmapContent`, `FlowLayoutEngine`,
  `CardDragGeometry`. Test targets follow the same rule.
- Date and age *wording* (`DateText`) is written by hand rather than with `DateFormatter`, so
  output is locale- and platform-independent (the app is English-only).
- `App/` is outside the package and never compiles on Linux at all.
- On Linux, `swift build` prints 11 harmless `no rule to process file … xcstrings/assetcatalog` warnings.
  They are expected; do not "fix" them by deleting the `Resources` folders.

## 7. Sync safety rules (N3) — apply to every change that writes

1. New files are written atomically to a unique name; never append to a shared file.
2. Per-device files carry the device id in the filename.
3. Every read/write of vault files goes through `NSFileCoordinator` (only `GTDVault` touches the
   file system).
4. Not-yet-downloaded iCloud items are requested with `startDownloadingUbiquitousItem` and
   reported as `VaultIssue` until available.
5. Conflict copies (unresolved `NSFileVersion` conflicts, "… 2.md" duplicates) are surfaced as
   `VaultIssue`, never auto-resolved.
6. Undo is refused when a file it would touch has changed since (`ServiceError.undoStale`).
   An **ordinary** command has no such guard yet — a write built on a pre-rename snapshot
   duplicates a note rather than losing one (`docs/follow-ups/53-stale-write-guard.md`).
7. Tests and agents never touch the real vault. Use `GTDFixtures` or a temp copy.
